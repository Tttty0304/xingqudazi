### Part 1　原始需求存档（原文摘录）

- 课题：使用 AI 编程工具，从 0 到 1 完成一个可实际运行的全栈 Web 产品；提供基于不同兴趣主题的在线聊天室；用户可浏览房间、选择房间进入、与其他在线用户实时聊天。
- **原文明确授权的自由度**："聊天室主题、用户体系、交互方式以及具体产品功能可以自行设计和扩展" —— 这是候选人/AI 需要主动做设计决策的空间，不是缺陷。
- 产出要求：可运行、可体验的完整 Web 产品（前端+后台+数据存储）+ 完整代码 + 运行说明。
- 评审重点方向（原文列出 9 项，逐项对应关系见下方 Part 2）：产品功能与体验完整性 / 后台服务及整体架构设计 / 实时通信方案 / 服务可靠性与异常处理 / 日志监控可观测性 / 系统安全性 / 性能资源成本 / 测试与代码质量 / 部署及运行方式。
- 明确鼓励使用 AI Coding Agent 全流程参与，不限制 AI 生成代码比例，但要求候选人理解并对最终代码、方案、质量负责，且要能演示 + 讲解架构/方案/AI 使用方式。

### Part 2　需求理解

**需求概述**：搭建一个面向"兴趣话题"的多房间实时 Web 聊天产品，用户进站后可浏览房间列表、进入感兴趣的房间、与房间内其他在线用户实时收发消息；同时后台工程质量（架构、可靠性、可观测性、安全、性能成本、测试、部署）是评分重心。

**已确认功能列表（原文明确）**：
1. 多个基于兴趣主题的聊天室（房间）
2. 房间浏览/选择
3. 进入房间后与在线用户实时聊天
4. 用户体系（形态开放，需自行设计）

> **v2 修订（用户反馈后）**：原 v1 草案默认把好友链/私聊/多媒体消息/App端/内容审核系统
> 划为"不包含"，理由是题目原文侧重"多房间群聊"场景 + 评分重点在后台工程质量而非功能
> 广度，担心堆功能广度挤占可靠性/可观测性/安全/测试等工程质量项的时间预算。用户反馈
> 指出好友/关注、私聊等属于 IM 类产品的基础能力，采纳该判断，调整范围边界如下。

**范围边界（v2，待确认标 ⚠ 的三项）**：
- **P0 核心范围（必做）**：Web 前端 + 后端服务 + 数据存储 + 实时通信链路（房间群聊）+
  用户体系（注册/登录）+ **好友关系链（加好友/好友请求/好友列表）+ 私聊（1v1 消息）**
  + 若干预置兴趣房间 + 群聊/私聊消息历史 + 图片消息 + 基础内容安全（敏感词过滤/长度限制/
  举报）+ 可运行部署方式 + 运行说明文档。
- **P1 加分范围（时间允许再做，不影响核心交付）**：语音/文件消息、@提及、Web Push
  离线通知、更完善的内容审核（如审核队列/人工复核台）。
- **⚠ 待用户明确边界（见下方新增开放问题 #10-#12）**：
  - App 端 —— 默认理解为"响应式网页适配移动端浏览器"，非独立原生/跨端 App；
  - 离线推送 —— 默认理解为 Web Push（Service Worker + Notification API），非移动端
    App 推送（因为默认不做独立 App）；
  - 内容审核系统的"复杂"程度 —— 默认做到"基础内容安全"级别（敏感词/长度/举报），
    不默认建设审核队列或人工复核后台子系统。

**验收标准**：可运行可体验的完整产品；完整代码可提交；候选人能完整介绍整体架构、关键技术方案及 AI 使用方式。

### Part 3　技术方案

**方案概述**：前后端分离全栈应用。后端采用分层模块化单体（保留可拆分为微服务的模块边界，不做真实微服务部署），WebSocket 为实时通信核心，关系型数据库做持久化、Redis 做在线态与广播支撑，结构化日志+基础 metrics 做可观测性，Docker Compose 一键部署。功能范围覆盖群聊（兴趣房间）+ 好友关系链 + 私聊 + 图片消息 + 基础内容安全，语音/文件消息、Web Push、完整审核子系统作为 P1 加分项。

**关键技术决策**：

| 决策点 | 选择 | 理由 | 被排除方案 |
|---|---|---|---|

**远期扩展预留（P2，不占用本次 P0/P1 工作量，仅做设计预留）**：

针对用户提出的"AI-native 扩展方向——基于用户数据训练社交机器人代替用户进行第一轮社交活动"设想，当前阶段**只做架构预留，不实现**：

- `users` 表预留 `interest_embedding vector(768)` 列（`pgvector` 类型），维度按未来实际使用的 embedding 模型确定，当前先建列不写入真实数据；
- 潜在应用方向（均为远期，不在本次 Task 范围内）：用户兴趣相似度检索（推荐好友/房间）、历史消息/对话摘要向量化后做 RAG 检索、机器人基于用户画像 embedding 生成首轮破冰消息；
- 之所以现在就定 `pgvector` 而不是"以后需要再迁移数据库"，是因为**关系型数据库的选型是后期几乎不可逆的架构决策**（数据迁移成本高），而现在多加一个扩展/预留几列的成本几乎为零——这是"性能/资源使用/成本"与"架构设计"评分项里，用较低成本体现前瞻性思考的一个点。

**AI-native 二期扩展设计（社交替身机器人，用户明确提出的远期方向）**：

用户设想：基于用户数据训练"替身机器人"，在兴趣房间内按用户预设的关注事项进行前期交互，若双方（用户/机器人）对同一事项产生更深互动，则推入"待人工确认列表"并标明推荐原因，形成 AI-native 社交方式。该设想影响面比单纯"预留向量列"更大，需要在**数据生产、参与者模型、交互留痕**三层现在就做对应设计，否则历史数据无法补采。

> **v3 修订（用户反馈后）**：用户明确"不追求一次实现完美的 AI 推荐匹配能力，只要完成简单的能力展示即可，并说明预留了后续扩展可能性"。据此，「匹配与推荐」由原 v2 的"仅建表、生成逻辑列 P2 排除"**升级为 P1 简单演示版**：用规则化匹配（基于 `user_watch_topics` 关注事项关键词重合度 + 是否共处同一房间打分，不训练模型、不做 embedding 语义相似度计算），生成 `match_candidates` 记录并配一个最小可见的"AI 推荐"列表页（展示推荐理由文案、支持确认/忽略）。真实的机器人训练/推理管线仍明确排除（P2），不受本次修订影响。
