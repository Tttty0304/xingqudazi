# AI 在开发过程中的使用方式（Task13）

> `project_introduction.md` 明确要求"介绍...AI 在开发过程中的使用方式"，本文档
> 如实记录本项目从 0 到 1 的整个开发过程中 AI Coding Agent（本项目使用
> CodeBuddy AI 编程助手，基于 Agent 工具调用模式）实际承担的角色、具体工作方式，
> 以及人工介入的关键节点，不做美化/夸大。

## 一、整体工作模式：需求澄清 → 计划拆解 → 用例先行 → 编码验证 的循环

项目全程按下面的循环推进，每个功能模块（Task）都完整走一遍，而不是"AI 直接把
所有代码写完再统一测"：

1. **Brainstorm（需求澄清）**：AI 主动把用户模糊的一句话需求（"做一个兴趣聊天室"）
   扩写成结构化的技术决策问题清单（Plan 文档里的 ★1-★15），逐项与用户确认后再
   定稿，避免"AI 自己猜一个方案就开始写"。
2. **Plan（任务拆解）**：把确认后的需求拆成 Task0-Task20 的显式清单（见
   `docs/00-brainstorm-and-plan.md` Part5），标注每个 Task 的依赖关系与并行性，
   使大型任务可以分批交付、分批验证，而不是一次性生成整个仓库。
3. **Testcase（验收用例）**：编码前先写好接口级验收用例清单
   （`testcase/00-testcase-plan.md`），明确"怎样才算做完"，再进入编码。
4. **Work（编码）+ Verify（真机验证）**：每完成 1-3 个 Task，AI 会：
   - 编译 + `go vet` + 单元测试（`go test ./... -v`）
   - 重建 Docker 镜像，在真实容器环境里跑一遍
   - 用脚本（curl/Python）或真实浏览器（`playwright-cli`）驱动多用户场景验证
   - 把验证结果如实写回 work log 文档，包括**验证失败/踩坑的过程**，不是只记录
     "验证通过"的结论

## 二、AI 实际承担的具体工作

- **架构与技术选型建议**：如"WS 广播必须走 Redis Pub/Sub 而非直连"、"私聊会话
  用规范化的 (较小ID,较大ID) 键避免方向不同产生重复会话记录"等设计，均由 AI
  在编码前提出并说明理由，用户确认后再实施。
- **全部代码编写**：后端 Go 代码（API/Service/Repository/WS Gateway/纯 Go 实现的
  Web Push 协议栈）、前端 React 代码、数据库迁移脚本、Docker/nginx 配置均由
  AI 编写。
- **测试设计与执行**：单元测试（覆盖 service 层核心业务逻辑，`go test -cover`
  可查覆盖率）、集成测试脚本（`scripts/integration_test.py`）、真实浏览器多用户
  端到端测试（`playwright-cli` 驱动 2-3 个独立浏览器会话模拟真实用户交互）均由
  AI 设计用例并执行。
- **真实环境问题排查**：多个 bug 是在真实 Docker/浏览器环境验证时才暴露、由 AI
  自主定位并修复的，例如：
  - 前端 `VITE_API_BASE_URL` 默认值与代码内已有 `/api` 前缀叠加，导致请求路径
    变成 `/api/api/xxx`（仅在真实浏览器网络请求里才能观察到，接口层面的 mock
    测试不会暴露）。
  - PostgreSQL 对 `uuid` 类型列做 `= ANY($1)` 查询时，若传入非合法 UUID 格式的
    字符串会直接报错而非"查不到"，导致批量查询接口在边界输入下 500
    （用边界值测试主动发现，而非等生产报错）。
  - `elliptic.Marshal` 在 Go 1.21 后废弃，`golangci-lint` 接入后才系统性发现
    （此前只用 `go vet`，未覆盖 `staticcheck` 类检查）。

## 三、人工介入的关键节点（human-in-loop）

AI 没有"全自动"完成本项目，以下节点由用户明确决策，AI 不擅自替用户做主：

- **全部技术选型确认**：后端语言、数据库、实时通信协议、App 端形态、离线推送
  形态、内容审核完整度、机器人透明度披露方式等 ★1-★15 决策，均由用户在 AI
  给出选项/建议后明确拍板。
- **验证节奏的调整**：用户中途明确要求"降低验证密度，攒2-3个小task一起测"，
  AI 据此调整了后续所有批次的推进节奏，不是固定不变的流程。
- **方向性选择**：例如"前端页面优先补齐好友/私聊等 UI 闭环，还是先做 Task10-13
  收尾"这类多路径选择，AI 会主动列出选项，等用户明确表态后再继续，不自行决定
  跳过某个方向。
- **范围边界确认**：如"是否开放用户自建房间"、"内容审核是否需要做到人工复核台"
  等产品边界问题，均由用户拍板，AI 只负责列出选项与权衡。

## 四、AI 使用方式的局限性说明（如实标注）

- AI 生成的代码比例很高（几乎全部业务代码），但**每一处关键设计决策都有对应的
  人工确认记录**（见 `docs/00-brainstorm-and-plan.md`），符合课题要求的"不限制
  AI 生成代码比例，但要求能够理解并对最终提交的代码、技术方案和产品质量负责"。
- AI 的验证手段（真实 Docker 环境 + 真实浏览器多用户测试）比纯粹的单元测试更
  接近生产场景，但仍不能完全替代真实用户的可用性反馈——UI 细节的美观度/交互
  流畅度更多依赖 AI 对"良好 UX 实践"的训练知识，而非本次针对性的用户调研。
- 部分简化点（本地磁盘存储、固定敏感词表、规则化 AI 推荐）是在时间预算约束下
  AI 与用户共同确认的合理取舍，不是被隐藏的技术债，均已在
  `docs/13-architecture-and-adr.md`「已知简化点」中列出。
