## 二、为什么仍建议做一次云端部署和压测

当前已有本机基准数据，所以不是"完全没做压测"；但本机压测进程、Docker服务和操作
系统共享同一台机器的CPU/内存/网络，数据只能说明功能在一定并发下可用，不能作为
相对独立的容量结论。云端部署有两个直接价值：

1. **评委体验**：通过公网URL直接体验，无需在评委PC安装Docker/拉取镜像；
2. **验证质量**：服务部署在云机、压测从本地或另一台云机发起，可采集服务端
   CPU/内存/网络/容器状态，形成更可信的HTTP吞吐、WS连接与延迟结论；
3. **部署真实度**：验证公网HTTP/WS反代、环境变量、持久化卷、备份恢复和防火墙，
   补齐"本机能跑"与"交付可运行"之间的差距。

## 三、推荐的 Lighthouse 资源与选择原则

| 场景 | 推荐规格 | 适用范围 |
|---|---:|---|
| 仅现场演示 | 2核4GB、50GB SSD、5Mbps公网 | 少量评委同时访问、功能展示 |
| 演示 + 基础压测 | **4核8GB、80GB SSD、10Mbps公网** | 推荐，可稳定运行应用/DB/Redis，并采集资源指标 |
| 多实例演示 + 压测 | 4核8GB起，或两台2核4GB | 在同机容器或两机之间验证横向扩展 |

- 地域优先选离演示现场/评委近的地域；没有硬要求时选择账户中已有的可用实例所在
  地域即可。
- 建议 Ubuntu 22.04 LTS 或 Debian 12；开放 `80`、`443`，部署维护期可临时开放
  `22`；不建议把 Postgres `5432`、Redis `6379` 暴露到公网。
- 部署前需确认有一台**运行中**的 Lighthouse 实例。当前部署集成可查询/使用已存在
  的实例；不能在未获用户授权的情况下替用户购买或创建云资源。

## 四、云端部署实施计划（获得实例后执行）

1. 查询用户给定地域的运行中实例，结合规格、运行状态、公网网络选择目标实例；
2. 上传本项目代码；
3. 在服务器安装/确认 Docker Compose，使用生产环境专用 `.env` 设置：
   - 强随机 `JWT_SECRET`；
   - `CORS_ALLOWED_ORIGINS=https://<公网域名>`；
   - LLM API Key 仅写入服务器不入库的 `server/.env`，不写进 compose/README；
   - 固定 VAPID 密钥（若需要演示Web Push）；
4. 用 Compose 启动 PostgreSQL、Redis、server、client；用宿主机nginx/Caddy或调整
   client端口映射对外暴露 `80`（有域名时再配置TLS/HTTPS）；
5. 防火墙仅放行必要端口，跑 smoke/integration/multi-instance 验证；
6. 执行备份脚本，并记录首次可恢复备份；
7. 产出公网演示URL和环境说明，更新交接文档。

## 五、云端压测计划与结论边界

### 推荐方式

- 服务端：Lighthouse部署本项目；
- 压测端：本地电脑或第二台云机运行 `scripts/load_test.py`；不要与被测服务进程
  放在同一台机器，以减少资源争抢；
- 场景：至少按 `50 → 100 → 200` 梯度跑 HTTP `GET /api/rooms` 与 WS消息往返，
  每档重复2-3轮；记录成功率、avg/p50/p95/p99、服务端CPU/内存、容器重启次数；
- 稳定性：额外做10-30分钟WS连接稳态测试，并复用 `resilience_test.sh` 验证单实例
  故障降级/依赖恢复。

### 可对评审作出的诚实结论

完成上述计划后，可说："在指定规格的单云机环境、指定并发梯度和指定压测时长下，
得到某组可复现的容量与延迟数据。"不能说"系统可支撑任意并发"或"已具备生产SLA"；
未做多机跨地域、长时压测、资源极限探测和真实用户流量验证前，这些结论没有依据。

## 六、其他人如何在自己的PC拉起服务

项目本身已可跨机器复现：对方只需拿到代码、安装Docker/Docker Compose，执行：

```bash
cd v2
docker compose -f deploy/docker-compose.yml up -d --build
./scripts/smoke_test.sh http://localhost:8080
# 浏览器访问 http://localhost:8081
```

业务数据/上传图片不随代码迁移：Postgres 与 `media_uploads` 使用的是本机Docker
具名卷。若要迁移历史数据，应在旧机执行 `./scripts/db_backup.sh`，将生成的
`backups/*.sql.gz` 复制到新机，再执行 `./scripts/db_restore.sh <备份文件>`；图片卷
目前需要额外手工打包迁移，详见 `docs/18-backup-and-restore.md`。
