# 数据库备份与恢复策略（能力补齐项）

> 背景：此前项目对"数据库备份/恢复"完全没有任何说明或工具，是「部署及运行方式」
> 考察方向下的真实缺口——demo/评估场景可以接受简单的本地脚本方案，但"完全没有"
> 和"有一个明确记录、真实跑通过的最小方案"是两回事。

## 现状与定位

本项目数据库为单机 Docker Compose 部署的 PostgreSQL 容器（非云托管数据库），
因此备份策略采用最直接的 `pg_dump` 逻辑备份 + 本地文件保留，而不是依赖云厂商的
自动快照能力。**这是一个 demo/评估场景的最小合理方案**，生产环境应替换为：

- 云厂商托管数据库的自动备份 + PITR（Point-In-Time Recovery）能力；或
- 物理层面的 WAL 归档 + 定期全量备份（`pg_basebackup`），支持任意时间点恢复。

## 备份

```bash
./scripts/db_backup.sh [输出目录，默认 ./backups]
```

- 通过 `docker compose exec postgres pg_dump` 生成逻辑备份，`gzip` 压缩后存放在
  `backups/xingqudazi_im_<时间戳>.sql.gz`。
- **关键细节**：`pg_dump` 带 `--clean --if-exists` 参数，让备份文件自带
  "先 DROP 再 CREATE" 语句——这是本次编写脚本时真实踩过的坑：最初没加这两个
  参数，恢复到一个已经跑过 migrations 初始化、已有数据的数据库时，会产生大量
  `relation already exists` / `duplicate key` 报错（因为恢复的目标库几乎总是
  "已经初始化过"的库，而不是空库）。加上这两个参数后恢复变为幂等操作。
- 自动保留最近 14 份备份，超出的自动清理，避免磁盘无限增长。

## 恢复

```bash
./scripts/db_restore.sh <备份文件路径.sql.gz>
```

⚠️ **危险操作**：会完全覆盖当前数据库的数据，执行前需要输入 `yes` 二次确认。

## 真实验证记录（2026-08-19）

已在真实运行的 Docker Compose 环境中完整验证一轮"备份 -> 清空覆盖恢复 -> 校验
数据一致"：

1. 恢复前记录基准：`users` 表 365 行，`rooms` 表 4 行
2. 执行 `db_backup.sh` 生成备份
3. 执行 `db_restore.sh` 用刚生成的备份覆盖恢复（同一个数据库，验证"备份内容
   真实完整"而非仅"脚本跑起来不报错"）
4. 恢复后重新查询：`users` 365 行、`rooms` 4 行，与恢复前完全一致
5. 运行 `scripts/smoke_test.sh`，确认 `/healthz`、`/readyz` 均正常，服务在
   恢复后可以直接对外提供服务，无需额外重启

## 建议的备份频率（demo/评估场景参考值）

- 手动演示前：建议执行一次 `db_backup.sh`，避免现场操作误删数据无法恢复。
- 长期运行场景：可用 cron 定时调用 `db_backup.sh`（本仓库未内置 cron 配置，
  因为 demo/评估场景下由使用者自行决定是否需要，避免过度设计）。

## 已知限制（如实标注）

- 逻辑备份（`pg_dump`）在数据量增大后耗时会增长，且备份期间对源库有一定
  读取压力；当前种子数据规模下（几百行）耗时在 1 秒以内，未构成问题。
- 不支持时间点恢复（PITR），只能恢复到某次备份的那个时间点，两次备份之间的
  数据变更会丢失——生产环境需要更细粒度的恢复能力时，应采用 WAL 归档方案。
- Redis 数据（在线态计数器、登录限流计数器、登出黑名单等）**不在备份范围内**：
  这些数据本身设计为可重建/短 TTL 自动过期（在线态随 WS 重连重新建立，限流/
  黑名单计数器过期后自动清理），不属于需要持久化保护的业务数据。
